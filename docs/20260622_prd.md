看了，整体评价是：

> **功能做得挺多，也不是玩具项目，但现在最大问题不是功能，而是“代码组织和开源观感”。**
> 现在更像一个你自己不断加功能迭代出来的桌面工具，已经能用；但如果要推广、让别人 star、让别人参与，代码需要明显整理一轮。

## 先说优点

你这个项目不是空壳。README 里已经有完整的启动器能力：应用/文件/命令/插件搜索、拼音搜索、剪贴板、索引配置、错误日志、Codex/Windows alias 支持等。([GitHub][1])

工程化也不是没有。`package.json` 里已经有 `typecheck`、回归测试、e2e smoke、Windows/macOS 打包、electron-builder 发布配置。([GitHub][2]) 另外 TypeScript 开了 `strict: true`，这是好事。([GitHub][3])

Electron 安全方面也做了一部分：窗口里 `contextIsolation: true`、`nodeIntegration: false`，这两个是对的。([GitHub][4])

所以结论不是“代码很烂”，而是：

> **功能完成度可以，但架构债已经开始明显了。**

## 最大问题 1：文件太大，后面会越来越难维护

这个是最严重的。

`src/renderer/plugin-panel-impls.ts` 有 **20677 行，745 KB**。([GitHub][5])
`src/renderer/renderer.ts` 有 **3948 行，112 KB**。([GitHub][6])
`src/main/ipc.ts` 有 **1427 行，38.9 KB**。([GitHub][7])

这说明你的前端插件逻辑、UI 状态、DOM 操作、工具实现大概率都堆在一起了。

这对个人开发短期没问题，但推广开源项目会有几个问题：

1. 别人不敢改。
2. AI 工具改代码时容易误伤。
3. 一个插件出问题，可能影响整个 renderer。
4. 后续想加插件市场、插件启停、独立测试会很难。
5. GitHub 上别人点进代码，会感觉项目“不够工程化”。

### 建议拆法

先别大重构全项目，先拆最肥的 `plugin-panel-impls.ts`。

建议结构：

```text
src/renderer/plugins/
  json/
    panel.ts
    state.ts
    service.ts
  jwt/
    panel.ts
    state.ts
    service.ts
  sql/
    panel.ts
    state.ts
    service.ts
  port-helper/
    panel.ts
    state.ts
    service.ts
  file-hash/
    panel.ts
    state.ts
    service.ts
  markdown/
    panel.ts
    state.ts
    service.ts
  registry.ts
```

每个插件保持这个模式：

```ts
export interface PluginPanel {
  id: string;
  title: string;
  mount(container: HTMLElement): void;
  unmount?(): void;
}
```

然后 `plugin-panel-impls.ts` 只保留注册表：

```ts
import { jsonPanel } from "./plugins/json/panel";
import { jwtPanel } from "./plugins/jwt/panel";
import { sqlPanel } from "./plugins/sql/panel";

export const pluginPanels = {
  "webtools-json": jsonPanel,
  "webtools-jwt": jwtPanel,
  "webtools-sql-format": sqlPanel,
};
```

这样你以后加一个插件，不会再动一个 2 万行文件。

## 最大问题 2：插件系统还不够“插件化”

README 里现在已经列了很多插件：JSON、JWT、SQL、文件哈希、端口助手、二维码、Markdown、API 调试、CodeAgent Switch 等。([GitHub][1])

但从代码体量看，这些插件大概率是“写在一起的功能模块”，不是标准插件架构。

真正的插件系统应该有这些边界：

```ts
interface LiteLauncherPlugin {
  id: string;
  name: string;
  keywords: string[];
  commands: string[];
  panel?: PluginPanel;
  actions?: PluginAction[];
}
```

你现在建议先做 **内置插件标准化**，不用马上做第三方插件市场。

也就是说：

```text
第一阶段：内置插件统一协议
第二阶段：插件按目录拆分
第三阶段：插件启用/禁用/排序
第四阶段：外部插件加载
第五阶段：插件市场
```

不要一上来就搞插件市场，否则安全和兼容性会很麻烦。

## 最大问题 3：Electron 安全还可以再收紧

你现在窗口配置里有：

```ts
contextIsolation: true
nodeIntegration: false
sandbox: false
```

前两个很好，但 `sandbox: false` 建议后面改成 `true`。([GitHub][4])

尤其你的项目里有 Markdown 预览、API 调试、JWT、配置转换、release notes 富文本展示等功能，输入来源复杂。README 也提到 release notes 会以受限富文本方式渲染。([GitHub][1])

我看到 `renderAppUpdaterReleaseNotes` 里用了：

```ts
template.innerHTML = notes;
```

然后再做 `sanitizeAppUpdaterReleaseNotesNode`。([GitHub][6])

这个方向是对的，但建议你后面换成更明确的白名单策略，或者直接引入 DOMPurify 这类成熟库。你现在是桌面端，不是浏览器网页，但 Electron 一旦 XSS + IPC 权限处理不好，风险比普通网页更大。

建议优先级：

```text
1. sandbox 改 true
2. preload API 做白名单
3. 所有 HTML 渲染统一经过 sanitizeHtml()
4. 禁止插件直接拿 ipcRenderer
5. IPC 参数全部做 schema 校验
```

## 最大问题 4：IPC 文件偏大，主进程职责要拆

`ipc.ts` 已经 1427 行。([GitHub][7])

IPC 文件大，一般说明这些东西混在一起了：

```text
窗口控制
搜索
剪贴板
插件调用
设置
错误日志
文件选择
系统命令
更新检查
```

建议拆成：

```text
src/main/ipc/
  index.ts
  search-ipc.ts
  clipboard-ipc.ts
  settings-ipc.ts
  plugin-ipc.ts
  updater-ipc.ts
  system-ipc.ts
  diagnostics-ipc.ts
```

`index.ts` 只负责注册：

```ts
export function registerAllIpcHandlers(ctx: IpcContext) {
  registerSearchIpc(ctx);
  registerClipboardIpc(ctx);
  registerSettingsIpc(ctx);
  registerPluginIpc(ctx);
  registerUpdaterIpc(ctx);
}
```

这样别人一看就知道每块能力在哪里。

## 最大问题 8：命令命名有冲突感

README 里同时写了：


这会让用户疑惑：输入 `codex` 到底打开哪个？([GitHub][1])

```text

cursor：打开 Cursor
vscode：打开 VS Code
```

CodeAgent Switch 这个功能可以作为你项目的差异点，但命令不要和真实 App alias 抢名字。

## 我建议你现在按这个顺序改

### 第一优先级：先做“开源体面化”

这个最简单，收益最大。

```text
1. 删除 tmp 文件
2. 更新 README 过期内容
3. 补 keywords / author / license
4. 增加截图 / GIF
5. README 顶部加 Download 链接
6. 加 SECURITY.md / CONTRIBUTING.md
```

这一步做完，别人点进来感觉会好很多。

### 第二优先级：拆 renderer 插件

先拆 5 个最常用插件：

```text
JSON
JWT
SQL
Port Helper
File Hash
```

不要一次拆完 26 个。先把模式跑通。

### 第三优先级：拆 IPC

把 `ipc.ts` 拆成多个 handler 文件。

### 第四优先级：安全加固

```text
sandbox: true
IPC 参数校验
HTML sanitize 统一函数
preload API 白名单
插件能力权限模型
```

### 第五优先级：性能优化

你是启动器，用户最敏感的是：

```text
唤起速度
搜索速度
输入响应
窗口是否置顶
索引是否卡顿
```

建议后面做一个简单性能日志：

```text
appReadyMs
windowCreateMs
firstShowMs
searchLatencyMs
catalogSize
indexBuildMs
```

然后在设置页里展示“诊断信息”。这对用户反馈 bug 很有用。
