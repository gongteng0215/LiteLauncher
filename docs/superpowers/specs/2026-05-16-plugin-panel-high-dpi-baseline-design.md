# LiteLauncher 高 DPI / 小窗口插件面板回归基线设计

> 版本：V1.0  
> 日期：2026-05-16  
> 文档类型：回归设计 / 实施基线  
> 适用范围：搜索首页、默认可见插件面板、重点复杂插件面板  
> 当前目标：建立一套轻量但稳定的高 DPI / 小窗口排查、修复、回归标准，并在不频繁触发真实 smoke 的前提下，持续约束布局质量

---

## 1. 背景

LiteLauncher 最近连续落地了搜索首页自适应布局、图片提示词、CodeAgent Switch、Clipboard Workbench 以及多组 WebTools 面板优化。随着默认可见插件数量增多、面板信息密度提升，界面质量风险开始从“功能能不能用”转向“在高 DPI、小窗口、窄宽度下是否仍然紧凑、可扫、可操作”。

当前仓库已经具备两类基础保障：

1. 源码级 / DOM 级回归：覆盖 `plugin-panel-impls.ts`、`styles.css`、首页网格等结构约束；
2. Electron UI smoke：覆盖一批默认可见插件的主流程与窄窗不横向溢出断言。

但这两层还不够细，主要问题是：

- 回归入口存在，但不同面板的布局标准还不完全统一；
- 部分插件虽然“能显示”，但高 DPI 或窄窗下仍可能出现留白过多、首屏操作离得太散、局部信息块过高、按钮组换行不自然等问题；
- 真实 Electron smoke 成本较高，不能作为日常高频检查手段；
- 目前缺少一套“先全量排查，再按问题大小定点修复”的统一基线。

---

## 2. 目标与非目标

### 2.1 目标

本轮设计目标是：

1. 为搜索首页与插件面板建立统一的高 DPI / 小窗口验收标准；
2. 在不大改现有交互的前提下，优先修复真正影响可用性和观感的问题；
3. 扩充源码 / DOM / 轻量 E2E 断言，降低后续布局回退概率；
4. 将“真实窄窗验证”从高频日常动作，收敛为每轮收尾只跑一次的确认动作。

### 2.2 非目标

本轮不做：

1. 不重做整套设计语言；
2. 不为所有插件统一成完全相同的布局模板；
3. 不对每个插件都补完整交互型 smoke；
4. 不把高 DPI 回归扩展成全量截图比对系统；
5. 不借这次机会推进与高 DPI 无关的大规模 `renderer.ts` 拆分。

## 3. 范围

### 3.1 首轮排查对象

首轮做“全量基线排查”，但排查深度分层：

#### A. 首页与公共容器

- 搜索首页结果区
- 最近访问 / 置顶 / 插件分区网格
- 插件面板外层 shell、滚动容器、通用 workbench 布局

#### B. 默认可见插件面板

至少覆盖当前默认可见集合中的主要面板结构，不要求每个插件都跑全交互，但要求能判断：

- 是否横向溢出；
- 是否在窄窗下仍能首屏操作；
- 是否使用了合理的内部滚动与分区；
- 是否存在明显的大块无效留白或失衡拉伸。

#### C. 重点复杂插件

优先精查下列复杂或近期频繁调整的面板：

- `codeagent-switch`
- `clipboard-workbench`
- `webtools-password`
- `webtools-json`
- `webtools-cron`
- 搜索首页布局

### 3.2 后续批次候选

如果首轮查出共性问题明显，再继续扩展到：

- `hardware-inspector`
- `webtools-http-mock`
- `webtools-image-prompt`
- `cashflow-game` 的非战局工具视图

## 4. 高 DPI / 小窗口统一验收标准

所有首轮覆盖对象统一按以下 5 个维度判断：

### 4.1 不横向溢出

- 面板主表单、主工作区、关键内容壳层在窄窗下不能把 `.shell` 撑出横向滚动；
- 横向滚动只能出现在明确设计为横向列表的局部区域，不能出现在页面级容器。

### 4.2 首屏可操作

- 核心输入、主按钮、主结果区至少应有一部分同时出现在首屏；
- 用户不应在打开面板后立刻面对大段空白、远离操作区的布局。

### 4.3 内部滚动清晰

- 长列表、长详情、长日志、长预览要在子容器内滚动；
- 不能让整个外层面板无限变高；
- 不能让多个相邻区域同时承担不明确的滚动责任。

### 4.4 长文本与控件不炸布局

- 长标题、长路径、长 URL、长 token、长标签必须截断或换行；
- 按钮组在窄宽度下允许换行，但换行后仍应保持密集与可读；
- 表单字段、卡片摘要、诊断文案要避免单行撑爆或多行失控增高。

### 4.5 视觉密度稳定

- 顶部摘要、过滤条、分组卡片、结果面板之间应保持紧凑关系；
- 面板内部不应出现大面积“只有背景没有信息”的松散留白；
- 同一层级的区块在视觉上要有明确主次，而不是全部被拉成长条。

## 5. 方案对比

### 方案 A：基线排查 + 定点修复 + 分层回归（推荐）

做法：

1. 先统一标准；
2. 用源码 / DOM / 轻量窄窗断言把问题筛出来；
3. 只修真实暴露的问题；
4. 收尾时再做一次真实窄窗验证。

优点：

- 改动范围最可控；
- 与现有回归体系兼容；
- 最符合“不频繁跑 smoke”的使用约束；
- 能逐步建立稳定基线。

缺点：

- 首轮需要先做一遍排查整理，启动成本略高于直接改 CSS。

### 方案 B：共享样式统一整顿

做法：

- 先抽出更多共享 panel shell / grid / card / section 规则；
- 用一轮样式收敛去压大多数插件问题。

优点：

- 视觉统一收益大；
- 中长期维护成本可能更低。

缺点：

- 牵涉面大；
- 容易影响当前已经可用的个别插件；
- 一轮里更难控风险。

### 方案 C：纯人工巡检 + 快速修补

做法：

- 先肉眼扫重点插件；
- 发现明显问题就直接改；
- 测试只补最低限度。

优点：

- 启动最快。

缺点：

- 易漏边角；
- 对后续回退几乎没有防线；
- 返工概率高。

### 结论

首轮采用 **方案 A**。它最适合作为当前阶段的“稳定器”。

## 6. 推荐设计

### 6.1 总体策略

本轮按四层执行：

1. **结构盘点层**：梳理首页、公共 shell、重点插件的关键布局结构；
2. **轻量回归层**：补源码 / DOM / 窄窗 fit 断言；
3. **定点修复层**：优先修共享样式，其次修单插件特例；
4. **一次真实确认层**：仅在收尾跑 1 次真实小窗 / 高 DPI 验证。

### 6.2 排查顺序

#### 第一优先级：公共结构

- `.shell`
- 面板外层 form / panel shell
- 通用 workbench 双栏 / 三栏布局
- 通用 section / summary / actions 组

如果公共结构存在问题，先修公共结构，再看单插件是否仍需特例。

#### 第二优先级：重点复杂插件

- `codeagent-switch`
- `clipboard-workbench`
- `webtools-password`
- `webtools-json`
- `webtools-cron`

这些插件要重点观察：

- 列表和详情分栏的断点行为；
- 工具条和按钮组换行；
- 长文本区、预览区、说明区的内部滚动；
- “紧凑但不拥堵”的信息密度。

#### 第三优先级：其余默认可见插件

以“是否产生真实布局问题”为准，不做过度美化式改动。

### 6.3 修复优先级

问题按以下顺序处理：

1. 会导致内容看不见、操作点跑出屏幕、横向滚动的硬问题；
2. 会导致首屏过空、信息层级失衡、内容被拉得很散的中问题；
3. 不影响可用性、只是视觉还可更细的软问题。

### 6.4 共享样式策略

优先在以下方向做共享约束，而不是每个插件单独修：

- 面板最大高度与内部滚动责任；
- workbench 列宽与换行断点；
- 标题、摘要、chip、按钮组的文本约束；
- 结果列表与详情区的滚动边界；
- 小窗口下的 section 间距、卡片 padding、操作组换行。

只有在插件交互确实特殊时，才追加插件专属样式。

### 6.5 结构调整边界

允许的小结构调整：

- 重排面板内局部分组顺序；
- 将说明区下沉或改为折叠；
- 将过长的横向工具条改为换行按钮组；
- 将高频操作上提到首屏；
- 把“空得难受”的单列拉伸改成更紧凑的双列 / 栅格。

不做的结构调整：

- 不大改插件主交互范式；
- 不为高 DPI 回归重写整个面板；
- 不同时引入新的大型功能模块。

---

## 7. 回归设计

### 7.1 源码 / DOM 回归

继续扩展以下类型断言：

1. 关键 shell / workbench / detail / sidebar 结构存在；
2. 关键容器具备 `overflow`、`max-height`、`minmax`、换行约束；
3. 重点按钮组、摘要卡、结果区仍维持紧凑布局；
4. 已知容易回退的结构不要重新退回“大表单直铺满屏”。

适用文件：

- `src/test/plugin-panel-impls-regression.test.ts`
- `src/test/search-section-grid-style.test.ts`

### 7.2 轻量 Electron 窄窗断言

在现有 `src/test/e2e-plugin-panels-smoke.test.ts` 基础上增强，但遵循轻量原则：

- 仍以“打开面板 -> 检查 fit -> 做一个最小交互”为主；
- 不把每个插件都扩成完整业务回归；
- 新增更细的容器级断言，例如：
  - 面板主壳层宽度不溢出；
  - shell 无页面级横向滚动；
  - 主工作区在 620px 左右宽度下仍能操作。

### 7.3 最终真实验证

每轮实现结束只做一次真实确认，范围包括：

- 小窗口宽度验证；
- 高 DPI 或等效高缩放视图验证；
- 首页与重点复杂插件快速巡检。

如果前两层都已经提供足够证据，真实验证只承担“最后防漏”，不承担主要发现问题的职责。

---

## 8. 错误处理与失败策略

### 8.1 回归失败时

- 若源码 / DOM 断言失败，优先判断是结构回退还是样式选择器失效；
- 若轻量 E2E 断言失败，优先判断是：
  1. 页面级溢出；
  2. 局部容器宽度失控；
  3. 真实功能变动导致选择器不再适用。

### 8.2 修复时的约束

- 避免为了修一个插件，把通用 shell 改成更松；
- 避免把内容强行裁掉来“伪装不溢出”；
- 避免用魔法数字堆出只在单一尺寸下好看的布局。

### 8.3 验证失败时

- 先回到源码 / DOM 与 CSS 结构判断问题；
- 只有在定位不清时才追加更细的真实验证；
- 不把高成本 smoke 当作普通调试循环。

---

## 9. 实施拆分

建议实现分三步：

### 第一步：建立排查基线

- 盘点当前已有断言；
- 标出首页、公共 shell、重点插件的现有保护范围；
- 找出明显缺口。

### 第二步：补约束并定点修复

- 优先补共享布局约束；
- 再补重点插件的专属修复；
- 同步把高风险结构写进源码 / DOM 回归。

### 第三步：一次真实确认

- 跑 build；
- 跑相关回归；
- 最后只做 1 次真实小窗 / 高 DPI 验证。

---

## 10. 验收标准

本轮完成需同时满足：

1. 搜索首页在窄窗下不出现页面级横向溢出；
2. 默认可见插件主面板在轻量窄窗检查下不过界；
3. `codeagent-switch`、`clipboard-workbench`、`webtools-password`、`webtools-json`、`webtools-cron` 的首屏可操作性与内部滚动责任清晰；
4. 至少新增一批与高 DPI / 小窗口直接相关的源码 / DOM 断言；
5. 只在收尾做一次真实小窗 / 高 DPI 确认，不形成高频 smoke 依赖；
6. 不引入新的明显布局回退。

---

## 11. 风险与取舍

### 风险

1. 共享样式改动过度，影响原本稳定的插件；
2. 断言写得太细，后续小重构就频繁误报；
3. 只看窄窗，忽略了中等宽度下的尴尬断点；
4. 只修视觉松散，反而牺牲可读性。

### 取舍

- 本轮优先“稳住可用性和紧凑度”，不追求一次性审美统一；
- 断言以“约束结构与责任边界”为主，不锁死过多像素级细节；
- 有共性先修共性，没有共性再做插件特例。

---

## 12. 推荐执行顺序

1. 首页网格与公共 shell 基线检查
2. `codeagent-switch`
3. `clipboard-workbench`
4. `webtools-password`
5. `webtools-json`
6. `webtools-cron`
7. 其余默认可见插件快速扫尾
8. 一次真实小窗 / 高 DPI 确认

---

## 13. 结论

本轮不把“高 DPI / 小窗口优化”当作一组零散 CSS 修改，而是把它收敛成一套可重复执行的质量基线：

- 先统一标准；
- 再做轻量排查；
- 只修真实问题；
- 用更细的结构回归兜底；
- 最后用一次真实验证收口。

这能在不频繁打扰日常开发节奏的前提下，把 LiteLauncher 当前这批复杂插件面板稳定下来。
